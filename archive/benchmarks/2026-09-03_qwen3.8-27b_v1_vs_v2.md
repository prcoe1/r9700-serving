# 2026-09-03 Qwen3.8-27B — V1 vs V2 model runner (MTP3, fp8 KV)

A/B of the V2 model runner on the live default profile. vLLM v0.28.1rc0 has a
`VLLM_USE_V2_MODEL_RUNNER` env override (`config/vllm.py`, `use_v2_model_runner`
property); the stock default for this platform excludes Qwen3.8 (hybrid GDN is
not in `DEFAULT_V2_MODEL_RUNNER_ARCHITECTURES`, and the ROCm platform override
notes some models run "unsupported by MRV2 or slower with MRV2 on AMD GPUs").
Motivation: vllm-project/vllm#54498 measured Qwen3.8-27B draft acceptance
**higher on the V2 runner** (the M-RoPE draft-KV-slot bug in
`llm_base_proposer.py` is V1-proposer-only; K=6 ≈ -5.7% mean acceptance on V1,
growing with K). If V2 held up, higher acceptance = direct decode gain.
Verified in the pinned build before testing: MTP is in V2's supported
spec-methods list, V2 ships an `mtp/` speculator, and the V2 runner implements
the Mamba "align" pre-copy (`v1/worker/gpu/model_runner.py`).

Stack (both rows): vLLM v0.28.1rc0 + local patches (protocol.py overlay, #48375,
#53877), torch 2.13.0+rocm7.14, AITER v0.1.20 + gfx1201 UA patches,
`ROCM_AITER_UNIFIED_ATTN`, MTP3, TP=2, 256K max-model-len, fp8 KV (calibrated),
`--no-async-scheduling`, `--max-num-seqs 2`, `--gpu-memory-utilization 0.92`,
`--prefix-cache-retention-interval 1600`. Method: `llama-benchy 0.4.0`,
`--pp 2048 --tg 32 128 --runs 3`, thinking off, single request. All numbers
same-day (2026-09-03); box runs 55+ home-lab containers, so per-metric noise on
decode is ±10% across boots (visible within each runner below).

### Delta

- **pp2048: V2 +3.6–4.0%, consistent** (all 4 V2 runs ≥ 2849; all 6 V1 runs
  ≤ 2786; zero overlap).
- **tg32/tg128: no measurable difference** — ranges overlap within the
  per-boot noise band; V1 re-measured after the V2 boot to control for box
  load (its tg128 dropped 65.3 → 57.7–58.7 between boots, same order as any
  V1/V2 gap).

## Verdict: rolled back to V1

V2 is **correct** on this stack and **~4% faster on prefill**, but **decode is
flat** — the test's raison d'être (acceptance-driven decode gain via #54498)
was not confirmed: MTP acceptance is the same 2.7–3.4 band on both runners.
The 4% prefill (TTFT) win does not justify standing on a runner path that
upstream does not default for this platform ("slower with MRV2 on AMD" TODO),
while this repo's entire verification baseline (patches, depth sweeps,
stability history) is V1-built and every bump would have to re-qualify V2.
`VLLM_USE_V2_MODEL_RUNNER` stays commented out in `env/qwen3.8-27b.env`.

Revisit when: (a) V2 lands in the platform defaults for hybrid-GDN/Qwen arches,
(b) #54716 (M-RoPE draft-slot fix) changes the V1 picture, or (c) TTFT at full
256K context becomes the binding concern (a 4% pp win at depth would save
~8 s of the 202 s d256K prefill — worth re-testing at that point with a
d256K pp A/B, since the +4% here was measured at 2K prefill).
