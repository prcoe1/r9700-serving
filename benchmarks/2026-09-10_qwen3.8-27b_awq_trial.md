# 2026-09-10 — Qwen3.8-27B Quark AWQ-INT4 trial (qwen3.8-27b-awq)

Trial of `amd/Qwen3.8-27B-Quark-AWQ-INT4-W4A16` (AWQ INT4 weight-only,
activations bf16, group-128, `quant_method: quark`) on 2× R9700 (gfx1201),
vLLM v0.29.0 + backported loader, torch 2.13 / ROCm 10.0. Profile:
`env/qwen3.8-27b-awq.env` — bf16 KV, MTP3, 2048 chunk cap, MRV2, seq-2 cap,
otherwise identical to the live `qwen3.8-27b` (fp8 weights / fp8 KV) profile.

## Outcome: KEEP as alternative profile, do NOT promote to default

Decode wins big (+30–50% at every depth, holds to d200K) and weights shrink
10.3 GiB vs ~27 GiB, but prefill loses ~26% — and this repo's focus is
deep-context (prefill-heavy). The carried patch + kernel risk stay justified
only as an opt-in decode-optimized profile.

## What it took to boot

1. **Loader backport** (`patches/vllm/48606-quark-w4a16.patch`, pinned to PR
   head `52d2d48`, still OPEN): v0.29.0's Quark plugin has no W4A16 scheme.
   The PR base had drifted — 4 files needed rebase (see patch header for the
   full list). Two live bugs found while porting:
   - `QuarkW4A16Int4.__init__` called `super().__init__(keys)`; v0.29.0's
     `QuarkScheme` is a bare ABC → `TypeError` at load (fixed: plain attrs).
   - `MPLinearLayerConfig(...)` missed the required `has_g_idx` field
     (added `has_g_idx=False`).
   - Lesson (now in the patch header): `git apply` **silently truncates** a
     hunk body exceeding its `@@` count — always recount after editing a
     patch (one stale count crash-looped the server at import).
2. **flydsl yank** (general build break, not AWQ-specific): flash-attn's
   `third_party/aiter` pins `flydsl==0.1.9.dev599`, yanked from PyPI;
   bumping `FLASH_ATTN_REF` to HEAD does not help (same submodule pin).
   `Dockerfile.fullbuild` now seds it to `0.3.1` (the version `AITER_REF`
   builds against). Any `rebuild` was broken until this fix.
3. **Kernel surprise (positive)**: `choose_mp_linear_kernel` picks
   `RDNAHybridW4A16LinearKernel` (gfx11/gfx12) on gfx1201 — no Triton
   fallback needed. The "AWQ unsupported on AMD" compat-table concern does
   not apply to this MP-kernel path.

## Follow-ups (not blocking)

- MTP acceptance is lower under AWQ (drafter trained on BF16 target diverges
  from the quantized target). MTP3 still the right shape (pos curve decays
  84→63→52%); an MTP2-vs-3 A/B could squeeze decode further.
- No long-context *recall* A/B on AWQ (perf-only at depth); AMD's quality
  numbers are short-bench (GSM8K/PPL/BFCL-single-turn).
- Drop `patches/vllm/48606-quark-w4a16.patch` when a pinned `VLLM_REF`
  contains the merge (re-verify gfx1201 kernel coverage, not just the merge).
- Re-run this battery if spec decode changes (MTP off/V2-only) or on any
  NaN / `!`-spam / empty reply in the field.
