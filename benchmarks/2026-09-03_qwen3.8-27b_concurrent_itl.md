# 2026-09-03 — Qwen3.8-27B concurrent ITL: `--max-num-batched-tokens` A/B

**TL;DR**: a big prompt (100K+ tokens) prefilled alongside a co-decoding
request stalls that request's token generation by **150–200x** at the default
`--max-num-batched-tokens 8192` (inter-token latency 47 ms → p50 3.5–4.4 s,
p99 up to 9.8 s). The stall is pure chunk-step duration — KV usage peaks at
29–40%, nothing waits in the queue. Lowering the chunk budget to **2048**
halves it twice (p50 ~1.0 s, p99 ~1.5–2.0 s) with **no measurable TTFT cost**
on the big prompt and only −3.4% on short-prefill (pp2048) throughput.
**2048 adopted** for the `qwen3.8-27b` profile.

## Why the stall happens

vLLM V1's scheduler caps each step at `--max-num-batched-tokens`. With one
request decoding (A) and one big prompt prefilling (B), A receives one token
batch **per step**, so A's inter-token latency equals the step duration —
dominated by the prefill chunk in that step. On this profile the chunk ends
must also land on the Mamba align-mode checkpoint grid (attn block size
1600 on fp8 KV), so the *effective* chunk per step is the largest grid
multiple under the budget:

| budget | effective step | step @131K depth (1527 t/s) |
|-------:|---------------:|----------------------------:|
| 8192 | 8000 (+192 straggler) | ~5.2 s |
| 4096 | 3200 | ~2.1 s |
| 2048 | 1600 (one Mamba block) | ~1.05 s |

This predicts the measured ~2x halving per budget step and the p99>p50 spread
(straggler/partial chunks). **Corollary: a budget below 2048 gains nothing** —
the step is floored at one Mamba block (1600 tokens ≈ 1.05 s), so 1024 would
behave like 2048. 2048 is the effective floor for this profile.

Note: vLLM V1 is *always* a chunked-prefill scheduler — there is no
non-chunked mode to enable. The co-decoder is batched into every step (the
probe shows `num_requests_waiting=0` throughout, no preemption); the only
knob is the chunk size. Two alternatives that would *not* help:

- **Priority scheduling** reorders which *waiting* requests get admitted to a
  step; within a step the GPU still has to execute the prefill chunk's
  compute before the co-decoder's token can come out. It changes queue order,
  not per-step duration.
- **Prefill/decode disaggregation** would move the prefill off the decode
  engine, but that's not a feature of this single-engine TP2 stack.

So the co-decoder's ITL during a big prefill is bounded below by "one
Mamba-block of prefill compute per token" (~1 s at 131K depth) as long as
`--max-num-seqs 2` and the single engine are kept.

## Setup

- v0.28.1rc0 + local patches, AITER v0.1.20 + local patches, MTP3, fp8 KV
  (calibrated), `--max-num-seqs 2`, `--no-async-scheduling`,
  `--gpu-memory-utilization 0.92`, gfx1201 × 2 (TP2). Same host boot for all
  three configs (only the chunk budget changed).
- Probe: `benchmarks/conc_itl_probe.py` (new). A = ~16.8K-token prompt
  streaming 512 tokens (400-word essay, temp 0); B = 131K or 200K unique
  random-word prompt (max_tokens 16) fired at A's 32nd token batch; unique
  text per run (no prefix-cache interference). Records A's inter-arrival
  times in three windows (pre-B / B-prefill / post-B), B's TTFT, and samples
  `kv_cache_usage_perc` / `num_requests_{running,waiting}` every 0.5 s.
- Reference bench: `llama-benchy@0.4.0` c=1, pp 2048 + 131072, tg 32/128,
  3 runs, coherence test each config (all PASSED).
- A's pre-B baseline is stable across configs: p50 47.5–47.8 ms/batch,
  ~2.7–2.9 tokens/batch (MTP) ≈ 57–59 t/s.

| budget | B size | B TTFT | A p50 | A p90 | A p99 | A max | choke (p99/p50-preB) | max KV |
|-------:|-------:|-------:|------:|------:|------:|------:|---------------------:|-------:|
| 8192 | 131K | 87.9 s | 3518 ms | 6686 | 7254 | 7254 | 152.6x | 29% |
| 8192 | 200K | 166.9 s | 4370 ms | 8968 | 9821 | 9821 | 205.8x | 40% |
| 4096 | 131K | 87.4 s | 1912 ms | 2842 | 2993 | 2993 | 62.7x | 28% |
| 4096 | 200K | 165.9 s | 2324 ms | 3721 | 4084 | 4084 | 85.4x | 38% |
| 2048 | 131K | 89.0 s | 1014 ms | 1428 | 1532 | 1532 | 32.2x | 28% |

`max_running` = 2 throughout, `max_waiting` = 0 — no queueing, no
preemption; the KV pool (~631K tokens) is not the constraint at c=2.

## c=1 reference (same boot)

| budget | pp2048 (t/s) | tg32 @d0 | tg128 @d0 | pp131072 (t/s) | tg32 @131K | tg128 @131K |
|-------:|-------------:|---------:|----------:|---------------:|-----------:|------------:|
| 8192 | 2797 / 2800 | 62.0 | 64.1 | 1565.5 / 1565.4 | 46.8 | 47.9 |
| 4096 | 2826 / 2790 | 59.0 | 67.7 | 1582.7 / 1583.9 | 45.6 | 52.7 |
| 2048 | 2704 / 2707 | 65.6 | 62.4 | 1504±89 / 1567 | 33.6±21.9 | 51.9 |

- **TTFT on the big prompt is flat** across budgets (87.9/87.4/89.0 s at
  131K; 166.9/165.9/169.0 s at 200K): prefill is compute-bound, per-chunk
  overhead (Mamba state copies, graph boundaries) is negligible.
- **pp2048 −3.4% at 2048** (2707 vs 2797 t/s, tight runs): a 2048-token
  prompt crosses one extra step boundary → +27 ms TTFT. The only real cost.
- Long-context decode (tg @131K) is box-noisy across all three configs
  (±10% across boots is normal); no clear trend, coherence PASSED on every
  config.

## Decision

**Adopt `VLLM_MAX_BATCHED_TOKENS=2048` on the `qwen3.8-27b` profile**
(`env/qwen3.8-27b.env`). A co-decoder now waits ~1 s per token (p99 ~1.5–2 s)
during a 100K–200K prefill instead of 3.5–4.4 s (p99 up to 9.8 s), at a cost
of +27 ms TTFT on short prompts and nothing measurable on long ones.

Notes:
- The `qwen3.6-35b-a3b` profile already pins 4096 for an unrelated reason
  (its gated-delta layers force a 2112-token attention block).
- The other dense profile (`qwen3.6-27b`) is unchanged; it can adopt 2048
  the same way if its users hit the same symptom (same architecture family,
  but not measured).

## Revisit conditions

- **`#45238`/`#53479` prefix-cache fix lands**: repeated big contexts become
  cache hits → the uncached prefill window shrinks → the stall shrinks
  independently of this knob. Re-run the probe after any bump that lands it.
- **`#51599` async scheduling lands** (and we lift
  `--no-async-scheduling`): scheduling overlaps decode; re-evaluate.
- **If ~1 s ITL during a big prefill is still unacceptable**: 1024 is not an
  option (step floored at one 1600-token Mamba block); the remaining levers
  are the `--max-num-seqs` cap (deliberately kept at 2, see #35288) and
  upstream fixes.
