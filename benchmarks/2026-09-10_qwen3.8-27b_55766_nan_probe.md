# 2026-09-10 — Qwen3.8-27B #55766 probe: bad Mamba checkpoint → NaN logits

**TL;DR**: ran the targeted probe for
[vllm-project/vllm#55766](https://github.com/vllm-project/vllm/issues/55766)
(prefill ending 4–10 tokens past a block boundary writes a bad Mamba/GDN
checkpoint; a later block-aligned prefix-cache hit restores it → NaN logits,
token-0 `"!"` spam). All cases **CLEAN** on v0.29.0 + MTP3 — but the result is
**masked, not disproven**: the measured hit geometry backs off **2 blocks**
from the last aligned boundary, and the bad checkpoint sits *at* the last
aligned boundary, so under MTP3 it is **unrestorable** today. The upstream
repro (ngram) had no EAGLE last-block drop, so its hit reached the bad
checkpoint; our MTP3 stack's hit stops short of it.

## The bug and why v0.29.0 raised the exposure question

#55766 (2026-09-07, open; upstream repro: v0.28.0, Qwen3.8-27B BF16, block
816, **ngram** spec decode, TP2): request A with rendered prompt length
exactly `N*block + r` (r ∈ {4,6,8,10}; r ∈ {6,8} most reliable; r ≤ 3,
r ≥ 12, odd r clean) writes a bad Mamba/GDN checkpoint at the aligned
boundary `N*block` because the prefill ended 4–10 tokens past it. Request B
(A's messages + A's reply + a fresh ~2000-token user message) gets a
block-aligned prefix hit **up to `N*block`**, restores the bad checkpoint,
and — after prefilling at least one full block past it — emits NaN logits
from step 1. The bad block is then itself cached, so identical retries fail
until the cache turns over. `cache_salt` on B, or padding the **start** of A,
cleans it. Speculation was *not* active at the failing step; the issue's
author notes the ngram dependency is untested.

The v0.29.0 exposure concern (AGENTS.md watchlist): the dense-retention
default (#55760/#55861, the #53504 root-cause fix) makes even the *first*
identical-prompt repeat hit the prefix cache, apparently widening the window
where a bad checkpoint can be restored.

## Setup

- v0.29.0+rocm100.gfx1201, AITER v0.1.20.post1 + local patches, MTP3,
  `--no-async-scheduling`, V2 model runner, `--max-num-seqs 2`, fp8 KV
  (calibrated), gfx1201 × 2 (TP2).
- Live cache geometry (from `/metrics`): `block_size=1600`,
  `mamba_cache_mode=align`, `prefix_cache_retention_interval=None` (dense),
  `cache_dtype=fp8`. (AGENTS.md's "bf16 KV / block 832" note for this
  profile is stale; the committed profile is fp8/1600.)
- Probe: `benchmarks/nan_checkpoint_probe.py` (new). Cases N = 10 blocks:
  - A: single user message of random words whose rendered prompt is exactly
    `10*1600 + r` (r = 6, 8, control 20), built and **verified** with the
    froggeric template v22.5 + model tokenizer, cross-checked against the
    server's reported `usage.prompt_tokens` (exact match). thinking on,
    temp 1.0 / top_p 0.95 / top_k 20, max_tokens 300.
  - B: A's user message + A's full reply (reasoning + content) + a fresh
    ~2200-token user message, max_tokens 64. B's new prefill after the
    restored boundary is ≥ 1 full block, satisfying the repro's condition.
- Verdict: CORRUPTED if B's output is `"!"`-spam/empty (the stock build
  exposes no `corrupted_requests_total` — the counter in the issue came from
  the reporter's diagnostics patch); NO-HIT if B's prefix hit < 1 block.
- Fresh random content per case and per run (a bad checkpoint, once cached,
  poisons identical retries, so re-runs must not self-hit).

## Results

| case | A prompt | A output | B prefix hit (tokens) | B output | verdict |
|------|---------:|----------|----------------------:|----------|---------|
| r=6  | 16006 | coherent | **12800** | coherent | CLEAN |
| r=8  | 16008 | coherent | **12800** | coherent | CLEAN |
| r=20 (control) | 16020 | coherent | **12800** | coherent | CLEAN |

All three B requests restored an 8-block (12800-token) checkpoint and
produced coherent text; A's outputs were coherent in every case.

## The geometry that masks the bug under MTP3

The bad checkpoint is written **at A's last aligned boundary** (16000 here),
and a request only restores the checkpoint *at its hit boundary*. The
measured hit boundary for a repeat of A's prefix is **12800 = 16000 − 2
blocks** (consistent across all three cases, different r and content). Two
one-block back-offs are in effect and both are MTP-gated:

- the EAGLE/MTP last-target-block drop (`use_eagle_block_drop`, #53388
  family) — MTP draft writes land in the last target block, so it is not
  reusable;
- the speculative one-block back-off that `#53479` (open, not merged in
  v0.29.0) is meant to remove.

So under MTP3 the restorable boundary is always ≥ 2 blocks short of the last
aligned boundary — exactly where the bad checkpoint sits. B restored a good
mid-prefill checkpoint at 12800 and recomputed through the 16000 region,
never reading the bad state. The dense-retention "widened window" therefore
does **not** apply to this carrier while MTP3 and the two back-offs stand:
the first identical repeat hits the cache, but stops 2 blocks short of the
bad checkpoint.

The upstream repro's B hit reached `N*816` (the last aligned boundary)
because **ngram** speculation has no EAGLE last-block drop. That reach is
structurally unavailable on this MTP3 stack today — so the open question in
the issue ("is ngram required?") is moot here: with or without a bad write,
the bad checkpoint cannot be restored.

## Caveats

- The probe exercised the restore path (real 8-block hits, ≥ 1 full block of
  post-hit prefill) but not the bad checkpoint itself — the CLEAN verdict is
  "masked by MTP hit geometry", not "the bad write does not happen on
  v0.29.0".
- N = 10 blocks only (upstream verified N = 10/20/34/40 at block 816);
  r ∈ {6, 8, 20} (r ∈ {4, 10} available via `--sweep`, 2 trials each;
  skipped — the mask applies to the whole r window).
- `corrupted_requests_total` is not exposed by this stock build; detection
  was output-based (`"!"`-spam/empty), matching the user-visible symptom.

## Revisit conditions

- **Spec decode changes**: dropping MTP (or a bump that changes the
  EAGLE-drop / #53479 back-offs) lets the hit reach the last aligned
  boundary → the #55766 carrier becomes live → re-run the probe.
- **Any NaN / `"!"`-spam / empty reply in the field** on this stack:
  re-run immediately; client-side workaround is `cache_salt` (or pad the
  prompt **start**) when the prior prompt length mod 1600 ∈ {4,6,8,10}.
- **Upstream #55766 fix lands**: re-run after the bump (issue still open as
  of 2026-09-10; upstream repro in progress on SM89, no PR yet).
- Also re-run on any vLLM bump per the usual bump checklist (hit geometry
  can shift with #53479/#53388/#45238-family changes).
